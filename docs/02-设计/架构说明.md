# 架构说明

## 1. 数据流

```
模拟器 ──XADD──> Redis Stream(gate_events) ──XREADGROUP──> 消费者
                                                          ├─ SET metric:snapshot (TTL 5s) ──> 接口 ──> 大屏
                                                          └─ INSERT metric_window ──────────> 接口(序列/排行)
```

四段职责单一，段与段之间只有两个连接点（Stream 消息体、快照 JSON），都写在接口契约里，所以四个人可以并行开发。

## 2. 为什么是这个结构

选题建议用 Lambda 或 Kappa 架构。我们选了 **Kappa 的简化版**：只保留一条流处理链路，批处理那一路用 MySQL 承担历史查询。

理由：
- Lambda 要维护实时、批处理两套代码和两套口径，四个人两周内必然对不齐；
- 本项目的历史需求只是"看最近几分钟的曲线和排行"，一张按秒聚合的表就够，不需要离线重算；
- 少一套链路，就少一处口径漂移的来源。

代价：历史查询精度受限于落库粒度（每秒每站一行），做月度报表要另建汇总表。这在当前需求下可以接受。

## 3. 组件与失败处理

| 组件 | 挂了会怎样 | 当前处理 |
|------|-----------|----------|
| Redis | 采集写不进、消费读不到、接口拿不到快照 | 接口降级返回空快照，页面显示"暂无数据"；消费者与模拟器启动时先 ping，连不上直接给出提示退出 |
| MySQL | 历史与排行查不到，实时仍可用 | 消费者写库失败只记一次告警，继续写快照 |
| 消费者 | 快照 5 秒后过期，页面变空 | 数据仍在 Stream 里（消费组未确认的消息可重投），重启后从上次位置继续 |
| Web 服务 | 页面打不开 | 依赖容器仍在跑，重启即可，无状态 |

## 4. 关键设计选择

- **消费组而不是 `XREAD`**：进程重启后不会把已处理的事件重算一遍，也不会因为一次崩溃丢掉未确认的消息。
- **快照放 Redis 而不是查库**：页面每秒轮询，查库会打满 MySQL；快照是"当前值"，天然适合放缓存。
- **页面由 Django 渲染**：`web/` 作为模板目录，页面与接口同源，省掉 CORS 配置，也省掉一个前端构建流程。
- **纯函数做计算**：`stream/metrics.py` 不碰 IO 和系统时间，窗口起点由调用方传入，因此能脱离 Redis 写单测。

## 5. 扩展点

| 想加什么 | 改哪里 |
|----------|--------|
| 新的指标（如平均候车人数） | `stream/metrics.py` 加计算 + 契约加字段 + 落库加列 |
| 新的数据源（真实闸机） | 只需保证写入 `gate_events` 的消息符合契约 2.1，其余不动 |
| 告警推送 | 消费者在窗口结束时判断阈值，写一个 `metric:alert` 键，前端或 WebSocket 读取 |
| 多实例消费 | 消费组已支持，直接再起一个进程，注意落库要幂等（已用唯一键 + `ignore_conflicts`） |
