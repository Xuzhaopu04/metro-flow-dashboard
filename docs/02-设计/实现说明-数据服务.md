# 数据服务模块实现说明

> 对应分工矩阵第六节第 2 项，供报告第三部分直接引用。
> 代码位置：`api/views.py`、`api/urls.py`；时序图见 `docs/03-建模/13-时序图-数据服务.puml`。

## 一、职责边界与分层

服务模块只做三件事：取参数、查数据、按契约拼 JSON。聚合口径由 `stream/metrics.py` 在消费者侧算好并落库，
接口层不再二次计算，避免同一份口径在两处各写一遍、日后各改一套。这一取舍的代价是接口必须信任库里的数据，
收益是「窗口怎么算」只有唯一一处定义，对账时不用怀疑接口层。

对外提供三个数据接口（`/api/snapshot`、`/api/series`、`/api/rank`）和一个页面路由。
快照走 Redis，历史与排行走 MySQL，两类数据源的失败处理方式不同，下一节展开。
所有响应都带 `Cache-Control: no-store`——实时数据一旦被浏览器或中间层缓存，页面就会"卡住不动"，
而这种现象在排查时极易被误判成消费者停了。

## 二、失败处理：降级而不是把错误甩给前端

数据源故障时的目标是「页面能打开，显示暂无数据」，而不是让运维问题变成前端报错。
快照读 Redis 失败、键过期、JSON 损坏、内容不是对象，四种情况一律退化为空快照并返回 200；
MySQL 查询失败则捕获 `DatabaseError`，`series` 退化为 `points: []`，`rank` 退化为 `top: []`。

这里的取舍是：**降级信息不写进响应体**。曾考虑加一个 `degraded` 字段让前端区分"确实没数据"和"取不到数据"，
但这个字段契约里没有定义，加进去就等于单方面改接口，前端还得跟着改。最终选择用日志留痕——
每次降级打一条 warning，排障时从日志看，页面行为保持契约原样。
捕获范围严格限定在 `DatabaseError`，不用裸 `except`：连接失败、超时该降级，
而字段名写错这类编程错误必须暴露出来，否则会变成一个"永远返回空数据"的哑巴故障。

## 三、参数校验与时间口径

`series` 的 `minutes` 与 `rank` 的 `top` 校验规则完全一致（整数、闭区间、越界返 400 `INVALID_PARAM`），
因此抽成 `int_param()` 共用，边界数字集中在一处，改的时候不会漏改另一个接口。
参数缺省与传空串都按默认值处理——契约里"不传"和"传空"应当是同一个行为。
`rank` 的统计窗口固定为最近 5 分钟，不接受入参，这是契约 4.3 的规定。

时间字段统一用 `local_iso()` 换算到项目时区再输出。原因是 MySQL 在 `USE_TZ=True` 下取出的是 UTC，
直接 `isoformat()` 得到 `+00:00`；而快照里的 `ts` 由消费者按本机时区写成 `+08:00`。
两者同屏显示会差 8 小时，看起来像 bug，所以接口层统一换算，让同一个页面上所有时间戳时区一致。

**遗留问题**：契约第 1 节写「时间精确到毫秒（快照 `ts` 精确到秒）」，但契约 4.2/4.3 的示例
以及 `event_time` 之外的字段实际都是秒级。当前实现与示例一致（`timespec="seconds"`），
与规则文字不一致。这个口径需由契约维护人确认后统一，实现方不单方面改动。
